## 3. The capability audit changes the plan: most of this already exists

The mission proposes building a doubleheader-safe MLB identity layer and an
official-result settlement path. **Both are already implemented and in
production.**

### `lib/edgelab/mlb_schedule.py`

- `fetch_schedule(date)` → `statsapi.mlb.com/api/v1/schedule?sportId=1&date=…&gameType=R`
- `parse_schedule_games()` → `gamePk`, team ids, **`gameNumber`**, `scheduledStart`;
  a game without a `gamePk` is *skipped, never fabricated*
- `build_schedule_game_context()` → **refuses** when one team pair maps to
  multiple gamePks: *"refusing to guess which leg archived"*
- `resolve_doubleheader_candidate()` → matches on `gameNumber`
- `backfill_missing_game_pks_via_schedule()`

### `lib/edgelab/mlb_boxscore.py`

- `fetch_game_feed(gamePk)` → `statsapi.mlb.com/api/v1.1/game/{gamePk}/feed/live`
- `extract_game_status`, `extract_teams`, `is_final_status`,
  `extract_boxscore_teams`, **`payload_hash`**

### `scripts/edgelab/settle_markets.py`

Settles the full observed market universe from the MLB linescore, and already
implements the conflict rule Wave 0.06 asks for: it validates
`extract_teams(feed)` against the archived Game record for the same stored
`gamePk` and treats a mismatch as an **identity conflict**, *"never
fuzzy-matches an alternate gamePk to 'fix' this."*

### The consequence

**`edgelab-postgame.yml` never calls The Odds API.** Its chain is
`build_recommendations.py` → `repair_game_identity.py` → `settle_markets.py`
→ `ingest_existing_bets.py` → snapshots → `score_replay.py`, and outcome truth
comes from MLB Stats API keyed by `gamePk`.

> **The Odds API `daysFrom` horizon constrains `clv_update.py` only. It does
> not constrain the EdgeLab observed-market restore at all.**

That is the single most important finding in this mission, and it inverts the
priority: **Population A — the large missing population — is very likely
restorable today with no new architecture**, because its settlement path never
depended on the endpoint that expired.

### What is genuinely still missing

1. **A durable final-result cache.** Every MLB fetch today is live. Nothing on
   disk records a final score — confirmed: **zero** score or linescore fields
   across 950 game records in the whole `data/edgelab/games/` corpus. A replay
   six months from now depends on statsapi still answering.
2. **`clv_update.fetch_scores()` still uses the Odds API** for full-game
   scores, with `days_from = max(1, days_ago + 1)` against a 3-day cap — even
   though `clv_update.py` **already contains** `fetch_mlb_linescore()`, which
   `settle_markets.py` imports *from it* (`from clv_update import
   fetch_mlb_linescore`). The fix is a source swap inside one function, reusing
   a fetcher already in the same file. **No settlement formula changes.**

## 4. Proposed durable result record

Reuse, do not duplicate. Identity already lives in `data/edgelab/games/`; this
adds only the outcome sidecar, keyed by the `mlbGamePk` already present there
at 100 % coverage.

```
data/edgelab/game_results/<date>.jsonl
```

```json
{
  "schemaVersion": "1",
  "mlbGamePk": "823908",
  "gameDate": "2026-09-01",
  "scheduledStartTime": "...",
  "awayTeam": "STL", "homeTeam": "LAD",
  "doubleheaderGameNumber": null,
  "status": "Final",
  "awayScore": 3, "homeScore": 5,
  "linescore": { "innings": [ ... ] },
  "source": "MLB_STATS_API",
  "sourceEndpoint": "https://statsapi.mlb.com/api/v1.1/game/823908/feed/live",
  "fetchedAt": "2026-09-09T...Z",
  "evidenceHash": "<mlb_boxscore.payload_hash(feed)>"
}
```

`evidenceHash` reuses the **existing** `mlb_boxscore.payload_hash`.

### Write rules

| Case | Behaviour |
|---|---|
| identical result re-fetched | idempotent no-op |
| richer compatible evidence (e.g. linescore added) | deterministic enrichment |
| **conflicting final score for the same `gamePk`** | **FAIL LOUD + quarantine** — never overwrite |
| no `gamePk` | refuse; never key on date+away+home |

## 5. Result-source precedence (proposed, pending live validation)

```
OFFICIAL MLB STATS API   → outcome / settlement truth
KALSHI / SPORTSBOOK      → executable and closing PRICE truth
```

1. durable cached result, if present
2. else MLB Stats API live, then persist
3. Odds API used **only** for cross-check, never as outcome truth
4. disagreement → **refuse and quarantine**, never pick the convenient one
5. ambiguous identity → refuse

## 6. Doubleheader safety

`2026-09-04` is the doubleheader-sensitive date (4 records carrying
`doubleheaderGameNumber`) and is the correct rehearsal date.

**A `date + away + home` key is provably unsafe on every date in the window** —
the matrix records 9–15 team-pair collisions per date. Note the cause: game
records are *versioned* (a `kalshi_registry_snapshots` record superseded by a
`normalized_slate` one), so 30 rows carry 15 distinct gamePks. That is not a
doubleheader, but it collapses identically under a naive key. `mlbGamePk`
separates both cases; nothing else does.

CR-3 production market mapping is **not** touched. This layer must only avoid
amplifying it.

## 14. Is a durable game-result cache needed? — **USEFUL LATER**

Re-answered against live evidence rather than the original plan.

1. **Can the six partitions be reconstructed today from existing MLB APIs?**
   **Yes** — demonstrated on three dates, including one 8 days back.
2. **Is result data already persisted after reconstruction?** **Yes.** Each
   settled row carries `settlementEvidence` with `gamePk`, `gameStatus`,
   `actualValue`, `participationEvidence` and `sourcePayloadHash`, and the
   `CLOSING_LINE` / `POST_GAME_SETTLEMENT` snapshots freeze the payloads.
   Reconstruction is already self-documenting.
3. **Would a separate `game_results` sidecar materially improve
   reproducibility?** Only marginally. It would hold game-level scores that the
   settlement evidence already implies, and would become a **second truth store
   that can disagree** with the first — the failure mode this Wave exists to
   avoid.
4. **Is it needed for the legacy/root path?** That is the only place it earns
   its keep: `clv_update.fetch_scores()` still uses the Odds API with a 3-day
   `daysFrom` cap. But the cheaper fix is the source swap in §3 — routing that
   one function through `fetch_mlb_linescore()`, which is **already in the same
   file**.

**Verdict: USEFUL LATER.** Not required for this restore, and building it now
would add a duplicate truth store with no demonstrated need. Revisit only if a
future replay must survive MLB Stats API being unavailable.
